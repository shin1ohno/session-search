# Independent audit of the redactor translation

This audit checks the Rust redactor, its generated tables, the JSON reader, the
raw-line route and the conformance gates against the Python oracle
`vendor/memory-mcp/session_redact.py` and the Python client's
`Shipper._mask_line` / `_mask_chunk` (`ccs/ingest.py:166-174,319-341`). The
specification is the Python behaviour itself plus the approved differences in
[compat-deviations.md](../compat-deviations.md) (D2 and D3 for raw lines). The
redaction contract is at most 8 passes, returning the result of
the last pass even when it is not a fixed point; the audit checks the
translation against that contract and does not evaluate the contract itself.

The audited tree is `main` at `5f52b81`. The auditor did not write any of the
audited code. Every input was generated by audit-owned scripts, not by the
generators under `tests/conformance/`. Everything ran with CPython 3.13.5
(Unicode 15.1.0), Rust 1.99.1, `cargo --locked`, a release build, and
`PYTHONDONTWRITEBYTECODE=1`, in a throwaway clone.

## Summary

| Area | Result |
|---|---|
| Rule translation and guards | No difference on 633,239 audit inputs (texts, records, per-rule spans, pass-limit inputs, an audit corpus, cap boundaries). |
| Table generation | Committed tables equal CPython's own sets. The generator accepts three trailing-`\b` shapes that its post-match check cannot translate (finding F1). No r1 rule has those shapes. |
| JSON reader and writer | No difference on 349,901 grammar and float inputs. |
| Line route | No difference on 200,014 raw lines, including invalid UTF-8, after applying D2/D3. |
| Pass limit | No difference on 25,000 inputs whose Python loop runs 0 to 8 passes; for 3,694 of them the last pass's result is returned without a fixed point, as the contract requires. |
| Equivalence predicates | `subsumed-optional` is unsound in general (finding F2). It is sound for its only r1 use. |
| Gates | All conformance gates run in the required checks. The committed corpus alone does not detect four count/strip slips; the second-layer gates do (observation O1). |

No input was found where Rust masks less than Python, or where Rust and Python
differ at all, on the shipped ruleset. Both findings are latent: they make the
gates weaker for a future rule change, not wrong for r1.

## Method

Each part was checked in two ways: by reading the Rust code next to the Python
code it translates, and by a differential run in which Python decides the
expected value. The differential runs drive the built binary through its
`_conformance redact --requests` protocol (`crates/ccs/src/conformance.rs:133-211`)
and compare the output string, the count names and order, and the route.

Each audit comparison was itself checked by a negative control: a deliberately
wrong Python oracle (pass limit 7, ASCII-only strip, forward walk order, a
7-hex tag, no depth tombstone, no NaN/Infinity, no `url-credential`
lookbehind) produced between 18 and 236 mismatches in each run, while the full
runs below, with the unchanged oracle, reported 0.

## 1. Rules and guards

**Reading.** `one_pass` (`crates/ccs-redact/src/lib.rs:249-309`) applies the
rules in Python's order (`vendor/memory-mcp/session_redact.py:165-204`): private
key, the eight tagged kinds in `_TAGGED` order, bearer, URL credential,
`cfg-json`, `cfg-kv`. Each rule runs only outside existing placeholders
(`lib.rs:209-223`, Python `:151-162`). The replacement strings, the HMAC tag
over the UTF-8 match truncated to 8 hex digits (`lib.rs:244-248`, Python
`:147-148`), and the `config-secret` value test (`lib.rs:227-243`, Python
`:131-139`) match. The value strip uses the generated `SPACE` table, which is
Python's `str.isspace` set, not Rust's `char::is_whitespace`.

Leading `\b` and one-character lookbehinds are moved out of the regex into
position checks (`lib.rs:130-158`). For a guarded rule, `sub`
(`lib.rs:161-208`) tries each start position, checks the start guard, runs an
anchored leftmost-first match and then checks the trailing `\b`. Python would
instead backtrack into another match when the trailing `\b` fails. The two
agree only if no shorter match could satisfy the boundary. For r1 this holds:
the only rules with a trailing `\b` are `aws-key` and `google-api-key` (fixed
count) and `github-token` (a word-only class, so every shorter end lies between
two word characters). The alternatives of `aws-key` and `github-token` start
with different characters, so a failed boundary on one alternative cannot be
rescued by another. A mechanical scan of the r1 parse trees confirmed both
facts.

The record walk (`lib.rs:343-401`) visits values last-to-first, which is the
order of Python's LIFO stack (`session_redact.py:265-296`); this order decides
which string crosses `MAX_RECORD_CHARS`. Keys are masked in insertion order
with the same `#2`, `#3` collision suffixes. Both caps and the record budget
count characters, not bytes (`lib.rs:310-340`).

**Differential.** 250,000 generated texts and 50,000 generated records, built
from secret prefixes, runs of the threshold lengths (8, 16, 20, 35, 36, 60 and
their neighbours), and 82 context characters chosen for divergence risk
(`\x1c`-`\x1f`, `\x85`, `ſ`, `K`, `İ`, `ı`, combining marks, non-ASCII digits,
format characters, line separators). Output, counts and count order matched for
all 300,000 (49,816 of them changed by redaction), and Python's `detect_*`
returned the same kinds on the Rust output as on its own output.

300,000 per-rule span comparisons (every capture group, one rule at a time, so a
later rule cannot hide an earlier rule's error) matched; 56,655 of them had a
Python match. Value caps and the record budget were compared at
999,999 / 1,000,000 / 1,000,001 characters with 1-, 2-, 3- and 4-byte
characters and across list and object nesting: 39 cases, no difference. An
audit-built corpus in the shipped corpus format with 8,200 vectors and HMAC
keys of 1 to 768 bytes (including keys longer than the SHA-256 block) passed
`ccs _conformance redact`; changing one expected character in it made the runner
exit 1.

## 2. Table generation

**Reading.** `tools/gen_redact_tables.py` expands every character class by
asking Python's `re` which code points it matches (`:72-77,142-153`), so
`(?i)`, `\s` and `\w` follow Python. It refuses unsupported nodes (`:156-177`),
nullable rules (`:281-285`) and some trailing-`\b` shapes (`:223-233`). CI
regenerates the tables and requires them to be byte-identical to the committed
file (`tests/conformance/run.py:37-38`).

**Independent check.** Against CPython directly, without the generator:
`WORD` equals both `\w` and `isalnum() or "_"`; `SPACE` equals `\s`,
`str.isspace` and the set `str.strip()` removes; the three lookbehind classes
equal the Python classes under the rules' flags; every table is sorted and
disjoint, as the binary search in `lib.rs:56-68` requires; and `SOURCE_BLOB`
(`crates/ccs-redact/src/tables.rs:1`) is the git blob of the vendored oracle.

**Finding F1 (latent defect in a gate): the generator accepts trailing-`\b`
shapes that the post-match check cannot translate.** The generator is the gate
that should reject any rule whose trailing `\b` cannot be checked after the
match; its own description says it refuses any construct it cannot translate
(`tools/gen_redact_tables.py:8-10`). `check_tail`
(`tools/gen_redact_tables.py:223-233`) inspects only the last node before the
trailing `\b` and treats a lazy repeat like a greedy one, so it accepts three
shapes it should reject: a lazy repeat directly before the `\b`; a
variable-width repeat followed by further fixed-width nodes; and an
alternation whose alternatives differ in width. For each shape, hypothetical
rules were accepted with `Boundary` guards, and the translated behaviour
(anchored leftmost-first match, then the boundary check) finds no match on
inputs where Python matches, so a translated rule of that shape would mask
less. Table generation would not stop such a ruleset change; only the later
differential gates could.

r1 is not affected: its only rules with a trailing `\b` are `aws-key`,
`github-token` and `google-api-key`, and in each the node before the `\b` is
the last variable node, greedy, and either of fixed count or over word
characters only (section 1). The shipped `aws-key` pattern, run through the
same probe as a control, translated correctly.

## 3. JSON reader and writer

**Reading.** `crates/ccs-pytext/src/json.rs` follows CPython's scanner: JSON
whitespace only (`:58-63`); `\u` escapes with a surrogate pair joined only when
a low surrogate follows (`:103-110`); raw control characters rejected and
`\x7f` accepted; `NaN`, `Infinity`, `-Infinity`; the number grammar with
backtracking over an incomplete fraction or exponent (`:128-173`); duplicate
keys keep the first position and the last value (`:283-288`); integers over
4,300 digits flagged (`:167`). The writer reproduces `float.__repr__`,
including round-half-even at decimal midpoints (`:406-528`), and Python's
escape set (`:530-565`).

**Differential.** 349,901 inputs: token-level near misses (BOM, `\x0b`,
`\xa0`, `U+3000` between tokens; `\U0041`, `\x41`, three-digit `\u`; `1.`,
`.5`, `1e`, `-`, `--1`, `+1`, `0x10`, Arabic-Indic and full-width digits;
`nan`, `-NaN`, `+Infinity`), 100,000 random decimal strings with 1 to 25
significant digits and exponents from -330 to 310, and `repr`, `%.17g` and
`%.16g` of 49,967 random finite doubles. Acceptance and the
`json.dumps(..., separators=(",", ":"))` bytes matched for all of them.

## 4. Line route

**Reading.** `mask_line` (`lib.rs:483-530`) skips a line made only of
`bytes.strip()` whitespace (`:487-497`), decodes with replacement like
`raw.decode("utf-8", "replace")` (`:498`), parses with the depth bound 64
(`:500`), and sends an unparseable line through `redact_text` like Python's
`except ValueError`. It tombstones a parsed line for a raw lone surrogate,
then depth over 64, then an integer over 4,300 digits, in the priority D2/D3
require, with empty kinds and the original offset. Python's route is
`_mask_chunk` then `_mask_line` (`ccs/ingest.py:319-341,166-174`).

**Differential.** The expected value is the real `Shipper._mask_chunk` of
`ccs/ingest.py` with the vendored redactor, to which the D2/D3 policy was then
applied as written in `compat-deviations.md` (not taken from the corpus
generator). 100,014 generated lines (nested to depths 1 to 200 with surrogate,
secret and huge-integer leaves; duplicate keys with the secret first or last;
escaped surrogates and pairs; 39 number spellings; 13 invalid UTF-8 sequences;
leading and trailing whitespace including `\x0b`, `\x1c`, `U+0085`, `U+3000`
and a BOM) produced 35,055 record, 54,272 text, 10,637 tombstone and 50 skip
routes, and matched in route, output bytes and counts. A further 100,000 lines
of random bytes (70% `0x80`-`0xff`) inside string and key positions matched,
which compares `from_utf8_lossy` with Python's `replace` decoding on every
route.

## 5. Pass limit

**Reading.** `mask_text` (`lib.rs:310-327`) returns early over the value cap,
then on a failed anchor prefilter, then loops at most `MAX_PASSES = 8`
(`lib.rs:45`) times, stopping when a pass changes nothing, and returns the last
text either way. This is Python's `_mask_text` (`session_redact.py:207,222-234`).
Counts accumulate over all passes in both.

**Differential.** 20,000 audit-generated texts, plus 5,000 records that carry
them as keys, values and list items. Python ran 0 to 8 passes on them
(histogram 83 / 980 / 1,802 / 2,959 / 2,825 / 2,038 / 2,061 / 1,488 / 5,764 for
0 to 8 passes), and for 3,694 the result of the last pass was returned without
a fixed point, as the contract requires. Rust matched all 25,000 in output and
counts. The corpus has vectors that fail
a limit of 7 (4 vectors) and of 9 (3 vectors).

## 6. Equivalence predicates

**Reading.** Survivors of the mutation gate count as equivalent only if one of
six predicates (`tests/conformance/classify_survivors.py:26-33,153-179`) holds
and a constructed-input hunt finds no difference. For the r1 rules:
`fixed-count`, `full-match`, `disjoint-continuation` and `run-determined` hold
for the reasons their table states. `end-anchored` checks only that the repeat
body is one node, not one character wide; this is harmless here because the
only use is private-key's `[\s\S]*\Z`, which has no capture group.

**Finding F2 (latent defect in a gate): `subsumed-optional` accepts mutants
that are not equivalent.** The equivalence classifier is the gate that should
call a surviving mutant equivalent only when it cannot change any span.
`subsumed_optional` (`classify_survivors.py:130-150`) checks that the optional
group is followed by the last, unbounded repeat of its sequence and that the
group's characters are inside that repeat's class, but not that the repeat is
greedy. When that repeat is lazy and the sequence is followed by more pattern
outside it, the optional group's mutants (`swap-greed`, `hi+1`) change the
match span, yet the real predicate code classifies them as
`subsumed-optional`. The same shape with a greedy repeat was classified the
same way and was, correctly, equivalent. A non-equivalent survivor of this
shape would be accepted unless the constructed-input hunt happened to find the
difference. The predicate soundness gate
(`tests/conformance/predicate_soundness.py:12-21`) cannot find this, because it
applies the predicates only to mutants that some input already killed.

r1 is not affected: the predicate's shape occurs only in `openai-key`
(`(?:proj-)?[A-Za-z0-9_-]{20,}`), where the following repeat is greedy and ends
the pattern, so its use there is sound.

## 7. Gates

All conformance gates (`tests/conformance/run.py`) run from
`tools/test_foundation.py:149` in the `rust` job's "Foundation, cross-check and
locking gates" step (`.github/workflows/ci.yml:45`). The required check
`test-python3` fails unless `rust` succeeded (`ci.yml:76-83`), so every gate is
required. The latest `main` run executed every step through `mutation-audit`
and printed `PASS all conformance gates`.

**Observation O1: the committed corpus does not see count-unit or strip-set
slips.** Applying four plausible translation slips to a copy of the Python
oracle and recomputing the 54,389 redact and detect vectors of the corpus
changed no expected value: a `config-secret` value length, the value cap, or the
record budget counted in UTF-8 bytes, and a value strip limited to ASCII
whitespace. The pass-limit changes were detected (above). Three of the four
slips are covered by the session-search negative controls
(`CAP-value-bytes`, `CAP-record-bytes`, `RECORD-rust-trim`), which the
second-layer regression inputs catch. A consumer that checks a shipped binary
with `ccs _conformance redact` and the corpus alone cannot see these slips; they
are protected by session-search CI, which the release workflow runs first
(`.github/workflows/release.yml:13-15`).

The fourth slip, a `config-secret` value length in bytes, has no negative
control. It was built as a Rust mutant (`maskable` counting `v.len()` instead
of `v.chars().count()`, `crates/ccs-redact/src/lib.rs:241-243`) and run through
every conformance gate that needs no further build, with the CI event's counts
and seeds. It passed the corpus, `json`, `strict-json`, `lines` and
`unicode-edges` gates and failed two: `differential` (21 output differences
and 1 key-order difference in 332,720 cases) and the structure-derived
comparison (322 differences in 631,265 requests). The slip makes Rust mask short
non-ASCII values that Python keeps, so it over-masks rather than leaks. The
audit's own text/record differential also found it (66 differences in 30,000
cases).

## Not covered

- Rust mutants were built for one behaviour only (above). The remaining gate
  sensitivity is taken from the repository's own negative controls, whose
  latest run passed, and from the Python-side corpus analysis.
- The weekly extended differential (2 million inputs with a per-run seed) was
  not repeated.
- Like the gates, every check here is finite. None shows equivalence on all
  inputs.
